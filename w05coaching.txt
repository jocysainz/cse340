Looking at your code:
const salt = await bcrypt.genSalt(10);

In your own words, what role does the salt play here, and why is it important not to just hash the plain-text password on its own?

--------------------------------------------------------------------------------
[STUDENT]
A salt is a random data added to a password before hashing so the output is unique. Without a salt, identical passwords produce the exact same hash, making it easy for hackers to crack them using precomputed lookup lists. adding a unique salt ensures that even if two users have the same passwords, their stored hashes are completely different, forcing attackers to guess each passwords one by one.

--------------------------------------------------------------------------------
[COACH]
Spot on! That is a textbook explanation—defeating precomputed rainbow tables and ensuring identical passwords don't yield matching hashes are the primary reasons we salt.

Now let's head into Topic 3: Protected Access Middleware.

Could you share a code snippet showing how you implement middleware to protect your routes (for example, checking if someone is logged in or verifying their role), and walk me through how it works?

--------------------------------------------------------------------------------
[STUDENT]
// src/controllers/users.js
const requireRole = (role) => {
    return (req, res, next) => {
        if (!req.session || !req.session.user) {
            req.flash('error', 'You must be logged in to access this page.');
            return res.redirect('/login');
        }

        if (req.session.user.role_name !== role) {
            req.flash('error', 'You do not have permission to access this page.');
            return res.redirect('/dashboard');
        }

        next();
    };
};

This middleware intercepts incoming requests to restricted routes before the actual page handler can run. First it checks req.session.user to see if the person is logged in at all if not, it flashes an error and redirects them to the login page. Next, it checks if the logged-in user's role matches the required role (like 'admin'), sending them back to the dashboard with an access denied message if they lack permission. If both checks pass it calls next(), which permits Express to move forward and safely load the requested page.

--------------------------------------------------------------------------------
[COACH]
You explained that beautifully, Laura! Higher-order functions returning middleware like requireRole(role) are such an elegant, reusable way to guard routes in Express.

What is the importance of having return statements before res.redirect(...) in those error conditions, and what might happen if you omitted them and let execution continue?

--------------------------------------------------------------------------------
[STUDENT]
The return statement immediately stops the function from running any further once a redirect is triggered. If you omit return, JavaScript will send the redirect response to the browser, but it will still keep running the rest of the code in the function eventually hitting next() or another response handler. Because an HTTP request can only receive one response, the server will crash with an error like Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client, and the unauthorized user might still accidentally trigger operations they shouldn't have access to.

--------------------------------------------------------------------------------
[COACH]
Spot on, Laura! That ERR_HTTP_HEADERS_SENT error trips up so many developers. Knowing that a response ends the HTTP exchange—and that code execution will proceed unless explicitly returned—is an essential insight for backend architecture.
