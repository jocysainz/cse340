const getProjectDetails = async (id) => {
  const query = `
    SELECT
      p.project_id,
      p.title,
      p.description,
      p.date,
      p.location,
      p.organization_id,
      o.name AS organization_name
    FROM project p
    JOIN organization o ON p.organization_id = o.organization_id
    WHERE p.project_id = $1;
  `;
  const queryParams = [id];
  const result = await db.query(query, queryParams);
  return result.rows.length > 0 ? result.rows[0] : null;
};

----------------------------------------------------------------------
[Coach]:
That is a clean, well-structured query function, Laura.

Looking at your SQL query, I notice you wrote WHERE p.project_id = $1 and passed queryParams = [id] rather than concatenating the id directly into the SQL string. 

What is the main reason you chose to use $1 and parameterized queries here instead of string interpolation?

----------------------------------------------------------------------
[Laura]:
The main reason is security specifically preventing SQL injection attacks.
If I concatenated or interpolated the variable directly into the string (like '... WHERE project_id = ' + id), a malicious user could pass SQL syntax in the URL (such as 1; DROP TABLE project;), and the database would execute it as code.
By using the $1 placeholder and passing [id] via queryParams, the database driver treats the value strictly as literal data rather than executable SQL command instructions. As a secondary benefit, parameterized queries allow the database engine to cache and reuse execution plans for better performance.

----------------------------------------------------------------------
[Coach]:
Spot on, Laura. You nailed both the primary defense against SQL injection and the query plan caching optimization. That covers our first topic smoothly!

// 404 Catch-All Middleware (placed after all routes)
app.use((req, res, next) => {
  const err = new Error('Page Not Found');
  err.status = 404;
  next(err);
});

// Centralized Error-Handling Middleware
app.use((err, req, res, next) => {
  console.error('Error occurred:', err.message);
  if (process.env.NODE_ENV === 'development') {
    console.error('Stack trace:', err.stack);
  }

  const status = err.status || 500;
  res.status(status);

  if (status === 404) {
    res.render('errors/404', {
      title: '404 - Page Not Found',
      message: 'The page you are looking for does not exist.'
    });
  } else {
    res.render('errors/500', {
      title: '500 - Server Error',
      message: 'An unexpected error occurred on the server.',
      error: process.env.NODE_ENV === 'development' ? err : null
    });
  }
});

----------------------------------------------------------------------
[Coach]:
This is an exemplary implementation of an Express error-handling pipeline, Laura.

Notice how your centralized middleware checks process.env.NODE_ENV === 'development' before deciding whether to print the stack trace to the console or pass the err object to the view. 

Why is it so important to hide full error details and stack traces from end users in production?

----------------------------------------------------------------------
[Laura]:
The main reason is security. Stack traces reveal server paths, database table names, and software versions that attackers could use to exploit the system. Hiding those technical details protects our infrastructure while providing users with a clean, professional error page instead of a confusing code dump
